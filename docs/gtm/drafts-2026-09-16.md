## Draft: DarkFactory issue 332

Source: `https://github.com/marius-patrik/DarkFactory/issues/332`

```md
This acceptance shape looks right to me. The detail I would make explicit is the receipt boundary for each chunk:

- planned chunk: files/directories expected to be touched, dependency edges, difficulty estimate
- workspace receipt: worktree path/branch/base commit, agent/provider, start/end timestamps
- verification receipt: exact command(s), exit codes, and artifact links
- merge receipt: commit hash merged back, conflict/no-conflict verdict, and dependency order used

The hardest failure mode in this pattern is a chunk that appears independent but writes shared setup/config/test fixtures. A cheap guard is to make each worker declare intended paths before it starts, then compare actual changed paths at merge time and turn overlap into an explicit resolution chunk.

For reference, Amux by Mixpeek has similar primitives in production: shared board with atomic task claiming, per-card dependencies/gates, run evidence, origin-stamped messages, and worker isolation. Not a drop-in for DarkFactory, but possibly useful as a concrete implementation to compare against while designing the receipts and merge semantics.
```

## Draft: Atomwright issue 14

Source: `https://github.com/getsyntegrity/atomwright/issues/14`

```md
One design suggestion: make the workspace lifecycle its own measured state machine instead of a helper hidden behind agent execution.

Useful states tend to be:

- `planned`: intended base commit, branch/worktree name, task id
- `created`: worktree path exists and points at expected base
- `running`: pid/session id captured
- `stopped`: exit status known
- `unknown`: process disappeared or probe failed; never treated as success
- `cleaned`: worktree removed or retained with a named reason

That gives you a clean place to enforce the failure semantic you already wrote: unknown process state is never assumed successful.

Amux hit similar rough edges running long-lived Claude/Codex/Gemini workers: the important part was not just starting sessions in worktrees, but making every probe say whether it was measured, and preserving enough receipt data that recovery does not depend on terminal memory.
```

## Draft: agent-workspace issue 31

Source: `https://github.com/yunaremaia/agent-workspace/issues/31`

```md
For this test suite I would split "real agent framework" coverage into two layers:

1. deterministic fake agent CLI in CI
2. optional real-agent smoke tests behind env flags

The fake agent should behave like a tiny Claude/Codex/OpenCode stand-in: read a prompt, write one file, optionally sleep, optionally fail, and print a recognizable done marker. That lets CI prove the important workspace contract without credentials:

- parallel worktrees do not share writes
- cleanup happens after success and failure
- timeouts do not leave orphaned process/worktree state
- logs/receipts name the worktree, branch/base commit, command, and exit status

Then add opt-in real smokes such as `AGENT_WORKSPACE_REAL_CLAUDE=1` / `...CODEX=1` for maintainers who have the tools authenticated locally. Amux uses this same distinction a lot: deterministic guards for the contract, real fleet checks for integration confidence.
```

## Draft: Codex issue 43148

Source: `https://github.com/openai/codex/issues/43148`

```md
Strong +1 on keeping this narrower than a full subagent task dashboard.

The compact state I would want in the main TUI is just enough to answer:

- is any delegated work still running?
- how many are active/done/failed?
- is the parent waiting on them?

Something like `Subagents: 3 running, 1 done, 0 failed` would already remove most of the repeated `/subagents` checks. If there is room for one interaction, pressing enter/clicking the indicator could open the existing subagents view.

One small implementation detail worth considering: include a stale/unknown state if the parent cannot currently measure a subagent. Hidden work is annoying, but hidden unmeasured work is worse because users will interpret the absence of activity as completion.
```
